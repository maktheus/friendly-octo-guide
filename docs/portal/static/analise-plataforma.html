1 · Como está sendo implementado visão micro — anatomia de cada serviço

Todos os 16 serviços seguem o mesmo padrão de 3 projetos. A regra central do repo: Domain puro nunca referencia infra (Kafka, Npgsql, HTTP) — é o que mantém a suíte de testes rápida e o gate de TDD viável no CI.

■ <Serviço>.Domain

Regra de negócio pura, determinística, sem IO. É onde os testes valem de verdade.

  • Ex.: AnomalyDetector (EWMA/z-score)
  • IshikawaClassifier (regras 6M)
  • ApprovalPolicy (guardrails)
  • PollCursor, TokenBucket, RouteTable

■ <Serviço>.Api / .Worker

Host de IO: Kafka consumer/producer, Postgres, HTTP. CI só compila — não executa. "Verde" aqui ≠ funciona.

  • Ex.: ScoringLoop, AlertConsumer
  • MesConnectorWorker, OutboxRelay
  • Instrumentação via Platform.ServiceDefaults

■ <Serviço>.Tests

Gate de CI: PR que muda src/** sem mudar o *.Tests é reprovado. Cobertura mínima de 80% no Domain.

  • Convenções: schema-first, outbox, quarentena/DLQ, "nada se perde calado"

Crítico · autenticação

Chave de assinatura JWT literal, duplicada em 3 serviços

"dev-only-signing-key-with-32-bytes!!" é o fallback em Gateway, Identity e Agents. Qualquer pessoa que leia o repo consegue forjar tokens de admin em qualquer instância que suba sem configurar Jwt:SigningKey. O próprio doc de prontidão reconhece; o CI deveria falhar hoje se detectar dev-only-* em ambiente Production — a regra está escrita mas não implementada.

Endpoint administrativo sem autenticação

Os endpoints admin do Identity operam com ator fixo "system:dev" em vez do token validado — ou seja, a trilha de auditoria administrativa (o objetivo da issue #5) registra ações sem saber quem as fez, e o endpoint não está atrás do RBAC.

🟠 Bugs de lógica no código

Bug · cross-service

Alerta do Predictive quebra a desserialização do Notifications (crash-loop potencial)

O ScoringLoop publica severity: "Warning" como string num objeto anônimo. O AlertConsumer desserializa para o enum Severity usando JsonSerializerDefaults.Web — que não inclui JsonStringEnumConverter. Resultado: JsonException (não null — o guard de nulo nunca dispara), o worker morre sem commitar o offset, reinicia, relê a mesma mensagem e morre de novo. Um único alerta de anomalia pode derrubar o pipeline de notificação em loop.

src/Predictive/Predictive.Worker/ScoringLoop.cs:66-73 · src/Notifications/Notifications.Worker/AlertConsumer.cs:43,71

Bug · detecção

AnomalyDetector: sensor estável nunca dispara anomalia (divisão-por-zero silenciada)

Se a variância é 0 (sensor flatline — comum em linha parada ou setpoint fixo), z = 0 por definição no código (stdDev > 0 ? deviation/stdDev : 0). Quando o valor salta, o z-score é zerado, isAnomaly = false, e a média absorve o salto — exatamente o "aprender o defeito" que o comentário do código diz evitar. O degrau mais óbvio de detectar é o único que nunca é detectado. Além disso, sem re-baselining, um deslocamento legítimo de regime (troca de produto) gera alarme perpétuo.

src/Predictive/Predictive.Domain/Scoring/AnomalyDetector.cs:31,35-40

Bug · i18n

IshikawaClassifier: tratamento de acentos inconsistente

O par estencil/estêncil tem as duas grafias, mas medicao só tem a forma sem acento — o texto real "falha de medição" cai em Indefinida (só salva se contiver "spi"/"aoi"/"calibr"). Sem normalização Unicode (remoção de diacríticos), cada regra precisa listar todas as grafias — e a lista já falha nisso. Além do mais, a ordem da lista decide a categoria em texto composto: "desgaste da pasta de solda" vira Máquina (desgaste vem antes), nunca Material — empate resolvido por acidente de ordenação, não por relevância.

src/Knowledge/Knowledge.Domain/Ishikawa/IshikawaClassifier.cs:31,49-53

Vazamento de memória

Dicionários que só crescem: TokenIssuer, IdempotencyLedger, detectores por sensor

TokenIssuer._familyOwner nunca remove famílias expiradas (uma entrada por login, para sempre); IdempotencyLedger._jobs guarda todo job Done eternamente; ScoringLoop._detectors cria um detector por sensor_id sem eviction. Em dev não aparece; num worker de longa duração é OOM lento e silencioso.

TokenIssuer.cs:19 · IdempotencyLedger.cs:18 · ScoringLoop.cs:15

Fragilidade · contrato implícito

Cursor MES comparado como string ordinal

PollCursor assume cursor "monotônico crescente, timestamp ISO ou id zero-padded, comparado ordinalmente" — mas nenhum código valida isso. Um MES que emita id numérico sem padding ("99" > "100" ordinalmente) silenciosamente descarta eventos novos como "já vistos". A invariante "nunca perde" depende de uma convenção não verificada do adapter.

src/Mes.Connector/Mes.Connector.Domain/PollCursor.cs:15-16,31

Inconsistência · schema-first

O tópico de alertas ignora o próprio contrato Avro do repo

A regra nº 4 do README é "Schema primeiro" e existe schemas/linha-alerta.avsc — mas linha.alertas.v1 trafega JSON ad-hoc: um objeto anônimo no produtor e um record duplicado (AlertMessage) em cada consumidor (Notifications, Agents). Três definições paralelas do mesmo evento, nenhuma validada contra o .avsc. É exatamente a deriva de contrato que a arquitetura promete impedir.

schemas/linha-alerta.avsc · ScoringLoop.cs:66 · AlertConsumer.cs:8 · Agents/AlertIngestService.cs

🟡 Estado em memória — "fase 0" que contradiz a promessa do bloco

Design · durabilidade

Cinco pontos onde a garantia anunciada morre com o processo

① Refresh tokens em memória: restart do Identity desloga todo mundo e a "revogação de família" não vale entre réplicas. ② Buffer store-and-forward da borda em memória: a única razão de existir desse buffer é sobreviver a queda — e ele não sobrevive. ③ Cursor MES: **FEITO** (persistido via `PostgresCursorStore`). ④ Ledger de idempotência da IA: **FEITO 23/07** (`ValkeyIdempotencyLedger` via `SET NX` + TTL com fallback em memória). ⑤ Rate limiter local: por réplica; o limite real vira N× o configurado. Tudo está documentado como "fase 1" — o problema é que os diagramas e a tabela de status vendem essas garantias como presentes (OK LOCAL) sem o asterisco.

🔵 Problemas da ideia / escopo

Estratégico · escopo

Pirâmide invertida: infraestrutura enorme, núcleo de pesquisa raso

O repo tem 16 serviços, 26 pipelines de CI, Helm + ArgoCD + Linkerd + Velero + MirrorMaker + Feast + MLflow + Marquez + OpenCost + Pyrra… para um time de 4 pessoas. Enquanto isso, o que as 3 dissertações de fato precisam entregar é hoje: ranking = ocorrências × 1.0 (o Random Forest não existe), classificação = ~21 palavras-chave, embeddings = feature hashing sem semântica, visão = zero código de modelo. Todo caminho crítico da pesquisa está bloqueado por dado externo (dataset SPI, rótulos do PIM, workshops de elicitação) — e nenhuma dessas dependências avança escrevendo mais YAML. O risco real do projeto não é técnico: é gastar o cronograma do mestrado polindo plataforma e chegar na banca sem resultado de modelo.

Estratégico · rótulo

"XAI" está superdimensionado nos textos

A "explicabilidade" atual é a string "3× · peso 1.00" e regras por substring. É um baseline honesto e defensável — mas os docs o descrevem como "ranking explicável (XAI)" e "sistema especialista", o que cria expectativa de SHAP/LIME/regras encadeadas que não existem. Numa banca, esse gap entre nomenclatura e implementação vira pergunta desconfortável.

Prático · toolchain

net10.0 + slnx: fricção de contribuição real

O monorepo exige .NET 10 (esta máquina tem SDK 8 — nem compila) e usa formato .slnx. Para um projeto que depende de colaboradores de mestrado com máquinas heterogêneas, o custo de entrada é alto e desnecessário — LTS (net8) faria o mesmo serviço.

Diagramação

Lacunas conhecidas ficam fora do diagrama principal

O mapa de fluxo mostra o caminho feliz completo, e as lacunas (WebSocket fantasma, Marquez sem bridge, e-mail que é log) ficam numa tabela separada no fim. Falta também um diagrama único "visão de pesquisa": qual serviço serve a qual dissertação — hoje isso está espalhado em 4 documentos.
